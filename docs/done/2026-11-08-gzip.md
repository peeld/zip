# 2026-11-08: gzip / gunzip, help groups, shared single-file UI

- New ops `gzip` (one file -> .gz) and `gunzip` (.gz/.tgz -> file), on
  `lib/gzip.js`. This is the first item in `docs/todo/new-ops.md`.
  - gzip uses native `CompressionStream('gzip')` and swaps the native 10-byte
    header for one with FNAME (Latin-1 names only, as the spec requires) and
    MTIME, like `gzip -N`.
  - gunzip reads the header when the file is dropped, shows the stored name,
    the time and the trailer's size, and suggests the stored name for saving.
    `[ View ]` shows the first 1000 bytes of the output.
  - **Multi-member .gz** (`cat a.gz b.gz`, bgzip): Firefox's
    `DecompressionStream` errors on anything after the first member and
    doesn't say where that member ended. `gunzip()` first tries the whole file
    as one member. If that fails, it tries each later `1f 8b 08` as the end
    of the member. The CRC/length check rejects a wrong guess, and output
    already passed on is skipped on the retry. Trailing zero padding is
    ignored, like `gzip -d`. 129 members of 64 KB take ~80 ms in Firefox.
- `core/transform.js` `transformOp(...)`: the whole UI for one-file-in,
  one-file-out ops. `core/streams.js`: `countBytes`, `readStart`,
  `streamToBlob`.
- `prepareSave().write()` takes a ReadableStream as well as a Blob. With the
  save dialog the stream goes straight to disk.
- `help` is grouped (`group` + `GROUPS` in the registry). `help <group>` and
  `help <cmd>` work. The viewer accepts an unknown total size (`null`).
- Gotchas found:
  - Firefox's `new Response(stream).blob()` turns a stream error into a bare
    AbortError. `streamToBlob` keeps the real message.
  - `Object.assign(obj, { get x() {} })` copies the getter's value once,
    not the getter.
- Tests: Python-made fixtures (named, no name, multi-member, bad CRC,
  bgzip-like). The browser writes a .gz that Python and `gzip -t` check.
  pickOp routing for .gz/.tgz. gunzip/gzip op mounts.
